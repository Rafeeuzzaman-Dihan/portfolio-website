# CLAUDE.md

Permanent architectural rules for this project. These are not suggestions — follow them for every change unless the user explicitly overrides one in the moment.

## Stack

- Nuxt 4 (`app/` directory structure), TypeScript, Tailwind CSS 4 via `@tailwindcss/vite`, ESLint (`@nuxt/eslint`), Yarn.

## Single-page architecture

This is a single-page portfolio site: one main page with anchor-linked sections (e.g. `#projects`, `#experience`, `#skills`). Do not introduce multi-page routing (`pages/` router-driven navigation) for the core site. New sections are added as components on the one page, linked via in-page anchors/smooth scroll — not new routes.

## Content lives outside components

Projects, experience, testimonials, and skills must live in structured content files (JSON or Markdown under `/content`), never hardcoded directly into `.vue` components. Components read from content files and render them. This keeps the site editable without touching component code. When adding a new content-driven section, create/extend a content file first, then build the component to consume it.

## Mobile-first responsive design (mandatory)

Design and implement mobile-first. Required breakpoints:

| Breakpoint | Width  | Target              |
|------------|--------|---------------------|
| (base)     | 375px  | Mobile              |
| `sm`       | 640px  | Large mobile / small tablet |
| `md`       | 768px  | Tablet               |
| `lg`       | 1024px | Laptop                |
| `xl`       | 1280px+| Desktop                |

Every component must be responsive-checked at all five breakpoints before being considered done.

## Theming: CSS custom properties via Tailwind v4 `@theme`

Theming is defined once, in CSS, via Tailwind v4's `@theme` directive (see `app/assets/css/main.css`). Only these tokens exist (values below are the **dark tone**; see "Dark and white tones" for the white tone):

- `--color-bg` — near-black base background
- `--color-bg-elevated` — panel/card background
- `--color-primary` — electric blue accent
- `--color-primary-light` — lighter blue, for hover states
- `--color-secondary` — muted slate-blue-gray accent
- `--color-text` — off-white body text
- `--color-text-muted` — dimmer gray-blue text
- `--color-border` — low-opacity blue-gray, for card borders
- `--color-live` — green, **status only**: live / online (Projects' LIVE bar, tab and Visit site button)
- `--color-alert` — amber, **status only**: classified / in progress (hazard-stripe bar, Classified panel, in-progress version)
- `--color-warm` — dark red, **small highlights only** (title squiggle, hover hard shadows, active-note and step lines): never body text or buttons
- `--font-heading` — Space Grotesk, for headings
- `--font-body` — Inter, for body copy
- `--font-mono` — JetBrains Mono, for small HUD-style labels and the hero terminal
- `--font-hud` — Rajdhani, condensed uppercase for Call of Duty-style HUD text (hero callsign)

No ad-hoc hex colors in components. The one exception is tech-stack brand colours: each skill in `content/skills.json` carries its real `brand` hex (content, not styling), used only for that logo's hover glow. Use the semantic tokens (e.g. `bg-(--color-bg)`, `text-(--color-primary)`, `font-heading`) everywhere. If a new color is genuinely needed, add it as a token in `@theme`, don't inline it.

Texture: **grain only** below the hero (see "Dark and white tones"). Two reusable background texture components still live in `app/components/backgrounds/` but only the **hero** uses one (`DotGridBackground`); do not add dot or blueprint backgrounds to other sections (the owner rejected dots as a background). The components: `DotGridBackground` and `BlueprintBackground`, auto-imported by Nuxt as `<BackgroundsDotGridBackground />` and `<BackgroundsBlueprintBackground />` (subdirectory-prefixed). Drop one inside a `relative` positioned section to add a subtle dot-grid or blueprint/linework layer that fades out at the edges via `mask-image`. Never use gradient blobs or generic AI-style gradient backgrounds.

A `section-container` utility class (defined in `main.css` via `@utility`) gives consistent max-width and horizontal padding across all breakpoints — use it as the outer wrapper for every section's content.

Clients are square **initials tabs** (names and roles shown from `lg`), each with its own timer line; the active note's large quote appears **word by word** with an outlined quote mark behind it. Notes auto-advance every 5s once on screen (the owner asked for a shorter time; one `NOTE_MS` constant drives both the advance and the timer line) (not under reduced motion); clicking a client jumps to it. Below that: the nav (blue line draws under a hovered link) and square social tiles, then only the copyright, **centred** (no logo, no "Built in Dhaka" line: both removed by the owner). Rejected: a huge outlined "DIHAN" wordmark and a back-to-top button (both removed by the owner), arrows and dots for the notes, the X link, a small "Text only, words from real projects" caption.
- Status colours still follow the rule: green is used only for the OPEN/transmitting status and the "Ready" mark.

### Dark and white tones (approved and implemented in `app/assets/css/main.css`, `app/app.vue`)

- The owner disliked the all-dark-blue look, then an all-white look, then every single accent colour offered (indigo, violet, vermilion, hot pink, teal, tangerine, volt, gold, cyan, mint, sky, black-and-white-only). The approved result is a **mix**: sections alternate between a **dark tone** and a **white tone**, with **Navy and dark red** as the accents. Do not propose other palettes unless the owner asks.
- **Order** (`app.vue`): hero dark, Expertise white, Experience dark, Projects white, Services dark (with How I work), Contact white, footer dark. Each section sets `data-tone="dark|light"` and everything inside flips, because components only read tokens. Tone values live in `main.css` (`[data-tone='dark']`, `[data-tone='light']`); add new colours as tokens there, never inline.
- **Dark tone = the original theme, unchanged** (it matches the hero). **White tone**: page `#f7f8fa`, cards white, text `#0b1020`, accent **Navy** `#1e3a8a` (hover `#172554`), live `#15803d`, alert `#b45309` (deeper than the dark tone so they stay readable on white). **Dark red** `--color-warm`: `#f4525b` on dark, `#b91c1c` on white.
- Tone-aware helpers: `--on-accent` (text on a filled accent button: use it for hover-flood buttons), `--lift` / `--hard` (card shadows: a hard dark-red offset shadow on white sections, a glow on dark), `--mono-filter` and the `.mono-mark` class (near-black logo marks ship as white `-dark` variants: GitHub, Vercel, AWS; the white tone inverts them). Any new dark-only assumption (white text on an accent fill, a black shadow, a white logo) needs a token, not a hard-coded value.
- **The hero is untouched and stays the owner's favourite** (typing animation, CRT PC): `.band-clean` removes grain from it. Never restyle it as part of a theme change; the owner explicitly asked for it to stay as is. No sticker, floating shapes, ticker, crooked cards or halftone dots (all tried in a prototype and rejected as "changed too much").
- **Section edge = ROUNDED SHEET (final, chosen by the owner from an Artifact of nine options)**: each section overlaps the one above like a sheet of paper, with big rounded top corners (`.band-seam` in `main.css`: `--slant` 36px to 70px, corner radius 0.8x, overlap 0.6x). Rejected, in order: a zigzag of triangles (hated), a single straight diagonal (liked first, then replaced), and an S-curve. Do not reintroduce diagonals, triangles or curves. The overlap is capped (70px max) so the hero's centred scroll cue is never covered: checked at 360 to 1920px (cue sits 31 to 56px above the hero's bottom, the overlap is 22 to 42px). No clip-path is used, so sticky How I work and `overflow-clip` are unaffected.
- **Backgrounds: plain white and plain black, with ONE texture on only a few sections** (the owner chose "hairlines and fine grain, few pages"; they rejected dots, halftone, per-section grain varieties and grain + grid together). `data-bg` on a band picks it: Expertise `lines` (fine 135-degree hairlines, 7% of the tone's text colour), Projects `grain` (fine film grain, 10%; inverted at 12% on dark), Services `lines`, footer `grain`. Hero, Experience and Contact are **plain**. Keep it this sparse and this faint; do not add a texture to the plain sections, and do not add grid, dots or blueprint patterns (the hero keeps its own dot-grid). Any new texture must be shown in an Artifact first.
- Title squiggle: every `SectionTitle` has an animated dark-red wavy underline. Each letter also hops and turns the accent colour when hovered.
- Other small interactions (mouse only, none under reduced motion): the How I work window leans toward the pointer on top of its scroll tilt and its blocks pop on hover; the Contact signal wave wakes up when hovered; social tiles lean toward the cursor like magnets; Expertise logos wiggle when hovered.
- Don't forget the case-study panel and navbar are not inside a tone (the panel is teleported to the body, the navbar is global), so they stay dark.

### Spacing and readability (agreed before publishing)

- **Smallest interface text is 11px** (mono labels, readouts, step labels). Only the miniature screens drawn inside the Services and How I work pictures go smaller, because they are illustrations. Do not add new text under 11px.
- **Card grids breathe**: 32px between cards from `sm` up (Projects: 32px across, 40px down), roomier padding inside Projects and Services cards, and one consistent gap below every section title (`mt-12`, `lg:mt-14`). More air between How I work and the cards above it. Prefer more space over more labels; but do not cut Projects card details (the owner rejected icon-only/cut-down cards).
- **Endless animations pause while off screen** (`useOnScreen`): the Services pictures and the Contact signal wave. New looping animations should do the same.
- The page has a title, description, `lang="en"`, theme colour and Open Graph tags in `nuxt.config.ts`; there is no share image or canonical URL yet (owner to supply). `public/resume.pdf` must be added by the owner for the Resume button to work. Testimonials and project screenshots are placeholders until the owner adds real ones.

### Process

- For a major visual change, prototype it as an Artifact first and get approval before changing site code.
- When a decision is genuinely the owner's, ask with concrete options instead of assuming.
- Record agreed design decisions in this file so they survive across sessions.

## No backend

This is a fully static site: no admin panel, no backend, no database. Content changes happen by editing files under `/content`, not through a CMS or API.
